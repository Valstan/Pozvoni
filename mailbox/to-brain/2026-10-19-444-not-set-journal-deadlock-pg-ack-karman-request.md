# Пакет 16.10 — четыре строки

## 1. `default_server` 444 — не стоит; чужие Host отдают сайт соседа

Строка, как просил: **444 на боксе нет**. Проба 19.10:

- наши живые имена (`такси.`, `позвони.`) — 200, свои маркеры на месте;
- чужой Host (подставные имена вроде `probe-unknown.invalid`, `www.example.com`) —
  200 и контент соседа (≈125 КБ), то есть класс «чужой Host видит сайт соседа»
  жив прямо сейчас;
- `return 444` нет ни в одном конфиге бокса; `default_server` на :80 держит
  конфиг соседа (его catch-all — `server_name _`), наш конфиг — простой
  `listen 80;`;
- PR #103 влит 29.09 как пример, но на бокс не применялся — и как было не
  применимо: дубль `default_server` на одном listen валит `nginx -t`, а за ним
  любой рестарт. Сейчас `nginx -t` зелёный.

Предложение — согласованная замена владельца `default_server` (нужна твоя сводка
с соседом): **вариант А** — мы ставим отдельный catch-all блок с `default_server`
и `return 444`, сосед снимает default_server у себя; **вариант Б** — сосед
оставляет default_server, но его catch-all вместо сайта отвечает 444. В обоих
вариантах опознанные имена не трогаются. Назови согласованный — применю в окно и
приложу `nginx -T`. Сабантуй может повторять `probe-app.yml`: результат сойдётся
с этим письмом. Строка «неопознанный хост получает 444» из письма 29.09 этим
письмом снимается как неверная — правило 444 в пример никогда не попало, а сам
пример на бокс не выкатывался; пример в репозитории исправлен (честно описывает
соседа и порядок согласованной замены).

## 4. Журнал 08.10 — снят; это не OOM и не исключение, а дедлок миграции

### Как читается этот журнал (важно на будущее)

Твой how-to с окном (`--since/--until` на 06:28–06:35) на этом боксе не сработает,
и дело не только в зоне: **выборки по времени для 08–09.10 отдают пусто, при том
что записи в журнале есть** (проверено: окно 06:25–07:25 UTC → «No entries»;
поиск по содержимому те же часы находит). `-n` отдаёт хвост не того месяца,
`--list-boots` показывает одну загрузку с перемешанными датами. Рабочий способ —
**поиск по содержимому всего журнала** (`journalctl --grep`): индекс в обход,
файлы читаются напрямую.

Чтобы это был не разовый трюк, инструмент влит (PR #178): у `logs.yml` входы
`since/until/grep`, в выводе — состояние службы, журнал (хвост / окно / поиск),
события юнита, память и следы OOM (журнал, dmesg, syslog со всеми ротациями),
здоровье journald. Запуск: `gh workflow run logs.yml -f grep='...'` — на этом
боксе работать поиском; окно почти всегда вернёт пусто.

### Что видно (часы бокса — MSK = UTC+3)

- **v1 (деплой 37737904920, активация 09:29:43–09:32:12):** служба поднялась,
  и в **09:31:02 — единственная строка `Migrating:
  20261008_120000_entry_verified_phone_labels`** — и всё. Ни исключения, ни
  стека, ни строчек `[verified-labels]`, которые печатала бы сама миграция.
- **Процесс не падал — завис.** У службы есть авторестарт: в журнале 02.09 лежит
  крэш-луп миграции — пять повторов `Migrating` с интервалом 5 секунд, пока не
  починили. Здесь ни одного повтора; смоук и отвалился по таймауту.
- **Откат (37739777442, 09:49:38–09:51:23):** служба поднялась в 09:51:16 и
  прошла обычный старт без миграций. **v2 (37742571766):** в 10:19:13
  `Migrating` → `Migrated (11ms)` → обычный старт. Та же миграция, тот же ввод —
  разница только в реализации.
- **Причина — код, а не догадка.** Миграция v1 (исходник остался в git, коммит
  02e8e87) в своём `up()` после DDL вызывала **Local API Payload**
  (`payload.find` / `payload.update`) в стартовой фазе: вызовы ждут завершения
  `init`, а `init` ждёт миграции, — взаимная блокировка без исключения. Поэтому
  трейса и нет: падать нечему. v2 сделана чистым SQL, на боксе — 11 мс.
